# MASTER ROGER DURABLE RULE — RDR-001
**Adopted by owner directive:** 2026-11-11
**Scope:** Every current and future project, website, platform, application, software build, specialist builder, AI agent, automation, Universal Next-Version Builder and recovery system—Teacher Roger projects and unrelated businesses alike.
**Authority:** Owner instruction. This rule is an additive, universal build prerequisite. It does not supersede more protective project-specific rules.

## Permanent command: Verify TWO independent latest authoritative baselines
Before beginning **every** new version, independently locate, inspect, and verify BOTH:

1. **Latest complete, usable actual application/software release.** This is the implementation/source baseline from which the next application/software is genuinely built.
2. **Latest authoritative Universal Next-Version Builder and associated independent native/specialist builder(s).** These govern mission, project ownership, all Roger Rules, requirements, acceptance gates, source history, recovery and maximum reasonable improvements. They have independent version histories. A coordinated PDF is not necessarily a native builder or a software release.

Do not conflate the two. Never assume the most recent builder contains the most recent software, or that the most recent software includes all builder requirements. Verify actual contents, completeness, provenance, integrity, test results, deployment correspondence and date/version evidence; do not rely on a filename, upload timestamp or untested assertion alone. If conflicting candidates exist, preserve them all and log the reason for the authoritative choice. If one source is blocked, disclose the gap and use the latest **verified accessible** baseline, clearly labeling it provisional where necessary.

## Mandatory discovery places, to the extent authorized and accessible
- ChatGPT Library and previous conversation artifacts, including separate project-specific folders.
- GitHub repositories, branches, commits, tags, releases, CI artifacts and referenced source archives.
- Render services, deployment IDs, environment/version metadata and linked source repositories **for the correct owner-approved workspace**. Never infer a workspace or make unintended changes.
- Google Drive, shared drives and project folders; Gmail attachments when relevant; and other connected storage, development, deployment or source-control services.
- User-provided ZIP, PDF and recovery packages, with nested archives / attachments and manifests inspected.

Discovery must be proportionate, evidence-driven, and repeated each build. Never say “latest verified everywhere” when a connector or workspace was inaccessible.

## Build, preserve, test, report
- Preserve previous source code, licenses, dependencies, data formats, configurations, content, assets, unique media, mission/ownership statements, all Roger Durable Rules, release and rollback history, verified baselines, several latest distinct usable versions, original complete recovery archives and subordinate specialist builder histories. **No destructive cleanup or overwriting as part of a build.**
- Maintain project boundaries and independently owned platforms. Read-only inspection does not authorize cross-project edits or deployments.
- Implement **maximum reasonable meaningful improvements** per new version, while keeping supported old functionality and avoiding purely cosmetic version inflation.
- Run unit, regression, browser/integration and security/privacy/consent tests appropriate to what changed. Explicitly distinguish tested, mocked, locally working, production deployed, provider connected and owner-approved functionality. Never fabricate pass results or claim real voice/avatar cloning when no generated sample was verified.
- Publish versioned change logs, dependency/integration contracts, integrity hashes, limitations, recovery/rollback procedure, current blockers and an evidence-backed baseline registry.
- Propagate the **exact complete rule** in every newly generated Universal Builder, next-version command, master rule register and new ControlCenter dispatch. Older builders must be updated only by their owning builder in a legitimate next version, preserving lineage.

## ControlCenter responsibilities
TR-ControlCenter coordinates baseline evidence, discovery checklists, rule distribution, work-order receipt/acknowledgment, compliance tests and status reporting; it does **not** silently merge, redeploy or modify independent products. For every specialist, require a dated signed-off baseline pair (software source identifier + builder identifier), confidence/evidence, gaps and safe release gates. Publish failures as blocked, not “done.”

## Short reusable command
> **RDR-001 applies. Before this build, independently verify the latest complete software/application AND the latest authoritative Universal Next-Version Builder across all relevant accessible sources. Preserve both version histories, all existing Roger Rules, recovery and rollbacks. Use maximum reasonable improvements, run regression/security/integration checks, and report what was actually verified versus unknown. Do not touch independent projects without authorization. Put RDR-001 unchanged into the next builder and release manifest.**

**Implementation status at initial issue:** Source document created for persistent Library storage and ControlCenter distribution. The rule is not automatically inserted into existing independent apps; each project must acknowledge and adopt it at its next authorized release.
