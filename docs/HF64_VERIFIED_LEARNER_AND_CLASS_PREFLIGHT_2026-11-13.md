## HF64 implementation work (complete in source, not yet production accepted)
- **Email-verified student-only class creation:** `POST /api/v2150/private-energy/sessions` must resolve an active student account with a positive email verification in either existing account metadata or verified email ledger. A merely active but unverified account is insufficient. This does not automatically de-enroll or alter any existing learner.
- **Actual ongoing course authorization:** Teachers, unlike owner/admin, may schedule the next session only when an assigned active or genuinely current upcoming class exists for the same private course. Completed, cancelled, expired, other-course, or unrelated historical classes cannot be used as implicit ongoing enrollment authorization. Owners/admins retain their established explicitly authenticated role pathways.
- **Server-verified external-calendar acknowledgment:** A dated class creation or manual Meet attachment requires explicit `external_calendar_acknowledged:true` in the protected request; form checkbox alone is insufficient. The class metadata records only a boolean teacher attestation; responses explicitly disclose `external_calendars_checked:false`. **Attestation is NOT real Calendar free/busy clearance**; do not infer external conflicts were resolved.
- **Class-specific read-only preflight:** `GET /api/v2150/private-energy/sessions/:id/confirmation-preflight?starts_at=...` requires a revocable account session, exact assigned teacher identity, valid future time, and existing DB/schema. It excludes the tentative class itself from internal conflict detection, reports whether the class is eligible for manual confirmation, blocks pending/coordination request states, and explicitly marks `google_calendars_checked:false`. No Calendar, email, billing, payment, meeting, or source file mutation.
- **Teacher classroom UX:** A per-class preflight control can run before manual confirmation; manual Google-calendar acknowledgment is transmitted to the server for both creating and confirming a session. Clear honest no-provider-integration copy remains.
- **Synthetic regressions plus browser qualification:** `scripts/verify-hf64-verified-booking.js` uses only a locally simulated Express/PostgreSQL transaction to exercise account verification, same-course teacher rights, explicit acknowledgment, overlapping class refusal, student/other teacher isolation, session-specific preflight, and no external actions. `tests/hf64-verified-booking.spec.js` checks browser flows and actual request bodies; both are included in `npm run check` and the mandatory full desktop/tablet/mobile/WebKit Playwright matrix.
